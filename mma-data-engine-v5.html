PROJECT: MMA Data Ingestion Pipeline PLATFORM: Replit (standalone project) PURPOSE: Collect MMA fighter data and news. Expose it via REST API. What the consuming app does with the data is not this app's concern. ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ THE ONE RULE ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Every fighter goes through the pipeline ONCE. Never again. Agent 1 checks the DB before anything runs. If the fighter is already there — the pipeline stops. Nothing happens. If the fighter is new — the pipeline runs: Agent 2 then Agent 3, back to back. After that the record is done. The main system handles all future updates. ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ TECH STACK ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Language: Python 3.11+ Framework: FastAPI Orchestration: CrewAI (4 agents — see below) Database: Supabase (Postgres) Scraping: BeautifulSoup4 (primary) + Firecrawl (fallback only) LLM: Claude claude-sonnet-4-20250514 via Anthropic API News search: Brave Search API Scheduling: APScheduler Env vars: SUPABASE_URL, SUPABASE_SERVICE_KEY, FIRECRAWL_API_KEY, ANTHROPIC_API_KEY, BRAVE_API_KEY SCRAPING STRATEGY — IMPORTANT: Use BeautifulSoup4 as the default scraper for all sources. Tapology and Sherdog are not JavaScript-heavy — BS4 handles them fine. Only fall back to Firecrawl if BS4 fails on a specific page. This keeps scraping costs minimal. JOB QUEUE — REQUIRED: Implement a pipeline_jobs table in Supabase to track every fighter moving through the pipeline. This costs nothing and makes debugging easy. Table: pipeline_jobs id uuid PRIMARY KEY fighter_name text fighter_id uuid REFERENCES fighters(id) status text -- queued / profiling / history / complete / failed error_log text created_at timestamp DEFAULT now() updated_at timestamp DEFAULT now() Agent 1 writes a row when it queues a new fighter. Agent 2 updates status to "profiling" when it starts. Agent 3 updates status to "history" when it starts. Agent 3 updates status to "complete" when done. Any agent updates status to "failed" + logs the error if something breaks. This gives full visibility into what's processing, done, or broken. ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ THE CREW — 4 AGENTS ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ AGENT 1 — EVENT AGENT ────────────────────── Trigger: Team inputs an event name via POST /events/scan OR scheduled daily at 8am UTC via APScheduler Job: 1. Take the event name 2. Search Brave + Firecrawl to get the full fight card 3. Extract every fighter name on the card 4. For each fighter — check DB: Already exists? Skip. Do nothing. Not found? Add to pipeline queue. 5. Create or update the event record in Supabase 6. Create fight_card entries (fighter A vs fighter B per bout) 7. Hand the queue of new fighters to Agent 2 Output: list of new fighter names to process + event/fight_card records written AGENT 2 — PROFILE AGENT ──────────────────────── Trigger: Called by Agent 1 for each new fighter in the queue. Back to back. Job — scrape profile data ONLY. Nothing else. Sources in order: Tapology → Sherdog → UFC Stats Fields to collect: Name, nickname, weight class Record: wins / losses / draws Record breakdown: KO wins / submission wins / decision wins Height, reach, date of birth, nationality Team / gym Profile image URL Verification: Scrape Tapology first, then Sherdog. Use Claude to compare every field between the two sources. Mismatch < 10%: set verified = true Mismatch >= 10%: set verified = false, log conflicts in review_notes Also collect during profile scrape: Twitter/X handle — search "[fighter name] MMA twitter" if not directly on source page Instagram handle — same approach Store both on the fighter record as twitter_handle and instagram_handle. These are used directly by Agent 5 — no searching needed later. Write fighter record to Supabase fighters table. Then immediately hand the fighter_id to Agent 3. Output: fighter record written to DB → fighter_id passed to Agent 3 AGENT 3 — HISTORY AGENT ──────────────────────── Trigger: Called by Agent 2 immediately after profile is written. Back to back. Job — scrape fight history ONLY for the fighter_id received. Sources in order: Tapology → Sherdog → UFC Stats For every fight in their career collect: Opponent name Result (win / loss / draw / no contest) Method (KO/TKO / SUB / DEC / UDEC / SDEC / MDEC) Round Time (e.g. "4:32") Event name Fight date Write each bout as a row in fight_history table linked to fighter_id. Then generate AI Brief using Claude and write to ai_brief field on fighter: fighting_style (striker / grappler / wrestler / hybrid) recent_trend (pattern across last 5 fights) strengths (array of strings) weaknesses (array of strings) prediction_insight (tendencies and patterns — not a betting pick) Set ai_generated = true on the fighter record. Fighter is now complete. Pipeline ends here for this fighter. This fighter will never be processed by Agents 1-3 again. Output: fight_history rows written + ai_brief written → fighter complete AGENT 4 — INTELLIGENCE & REPORTING AGENT (runs independently) ──────────────────────────────────────────────────────────────── Trigger: Every 45 minutes via APScheduler. Breaking signal types (injury, cancellation) run every 15 minutes. PURPOSE: Two layers. Both matter. LAYER 1 — STANDARD REPORTING The foundation. Keeps the app current and credible. Covers: fight announcements, cancellations, replacement fighters, weigh-in issues, event updates, promotional news. Written fast, written clean, delivered before the big outlets finish formatting theirs. Speed is the advantage here. LAYER 2 — INTELLIGENCE SIGNALS The real edge. Things that actually affect fight outcomes that most outlets don't connect or don't care about. This is what separates the app from everything else out there. Signal list — Agent 4 hunts for these specifically: Camp changes (new gym, new coach, late notice) Injury reports (official and unofficial — social, forums, podcasts) Fighter behavior signals (appearances, social activity, interviews) Weigh-in history and weight struggle patterns Sparring reports (coaches, training partners posting anything) Deleted social posts (screenshot sources, forum captures) Motivation signals (contract disputes, financial pressure, retirement talk) Travel and location signals (is he where he should be?) Replacement fighter flags (short notice = undercooked) Promotional red flags (fighter unhappy, political issues with promotion) When a signal is detected it gets flagged with signal_type tag so the app can surface it separately from standard news. WRITER PERSONA: Name: The Connect Voice: Hybrid insider and hype. Talks like someone who has been in and around the sport for years. Knows the fighters, knows the camps, knows the politics. Not corporate. Not a press release rewriter. Direct, confident, occasionally punchy. Speaks to fans who watch every card AND to people who have money on the line. Both audiences get what they need. Rules he always follows: Never over-explains — fans already know the sport Leads with the most important information first Fight announcements get energy — make it feel like an event Injury and signal reports are delivered straight — no drama, just facts and implications Never speculates beyond what the source supports Short sentences when it matters. Punch it. SEO basics baked in — fighter names, event name, promotion in the first 50 words. That is enough. Do not stuff keywords. Content is written to be shared, not to rank. Quality and speed create the viral loop — SEO just gets it indexed. SOURCES: Brave Search API — queries every cycle: Layer 1: "MMA news today" / "UFC announcement" / "fight cancelled" / "replacement fighter" / "fight card update" Layer 2: "MMA injury" / "fighter camp" / "sparring" / "fighter spotted" / "[fighter name] training" / "UFC roster" / MMA subreddits / MMA Twitter/X signals / fighter and coach social accounts via Firecrawl Firecrawl — fetch full content where Brave snippets are not enough. Priority sources: MMA Fighting, ESPN MMA, Sherdog news, BJPenn.com, MMA Junkie, fighter/coach social profiles. TWO MODES — assigned automatically based on fight schedule: MODE 1 — DEEP SCAN Fighter has a bout on a card in the next 30 days. Full scan every cycle. Every post, every story, every signal. This is the high-value window — the closer to fight night the better. Signals hunted: Weight and cut signals (food posts, check-ins, body content) Injury hints (boot, wrap, limp, hospital, cancelled appearance) Camp signals (new faces tagged, gym changes, coach posts) Mood and motivation (frustration, confidence, distraction) Unusual silence (account goes dark close to fight — flag it) Deleted posts (captured from forum screenshots where possible) MODE 2 — LIGHT WATCH Fighter is active in the DB but no upcoming bout in next 30 days. Lighter pass, less frequent. Only flags clearly significant activity. Keeps the radar warm without wasting cycles. HOW MODES ARE ASSIGNED: Agent 5 queries fight_cards for bouts in next 30 days. Any fighter_id on that list → MODE 1 deep scan. All other active fighters → MODE 2 light watch. Fully automatic. No manual management needed.
